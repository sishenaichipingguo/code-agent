## 第一篇（v2 总论）

### X / 即刻 thread（5 条）

**1/5**
用 Claude Code 用着用着我有个怪念头：这东西底下是不是就一个 while 循环？

拆了一下，发现真的就是。20 行代码就能跑通。

但"跑通"和"好用"之间，隔着四个工程问题。🧵

**2/5**
问题一：流式工具调用是碎片化的。

工具名来一个 chunk，参数来三个 chunk，你收到第一个就去执行——拿到的 JSON 是截断的，工具直接炸。

正确做法：先收集，等 done 再执行。用 Map 不用数组，因为 chunk 不保证按序到达。

**3/5**
问题二：跨进程上下文你不显式传，就一定丢。

我的记忆系统召回率低得离谱。排查一周，最后定位到一行代码：SESSION_ID 没传。

单进程靠闭包糊弄。跨进程，所有上下文必须当数据发出去。

**4/5**
问题三：语义召回阈值是调出来的，不是算出来的。

0.7 → 什么都召不回
0.1 → 召回一堆噪音
0.3 → 刚好

别人的 0.7 在你这里可能等价于 0.3。别信论文，在自己数据上跑。

**5/5**
问题四：并发安全要工具自己说，不要让框架去猜。

框架不知道 `bash git status` 是只读的、`bash rm -rf` 是破坏性的。让每个工具声明 `isConcurrencySafe(input)`，调度器一行搞定。

### 掘金沸点版（单条，300 字内）

从零写了一个 AI 编程助手（TypeScript + Bun），两个月后最反常识的发现：prompt 工程不是瓶颈。

真正决定 Agent 是玩具还是工具的，是四个纯工程问题：
① 流式工具调用的状态机
② 跨进程上下文传递
③ 语义召回阈值调参
④ 工具并发安全声明

每个都不需要 AI 知识，全是后端工程师该会的东西。这也是为什么大部分套壳产品体验差——他们解决了 prompt 问题，把工程问题留给了用户的耐心。

代码开源，全文在评论区 👇

## 第二篇（进程模型）

### X / 即刻 thread（4 条）

**1/4**
写 AI Agent 的记忆系统，第一版我把 embedding 挂在主循环里。

本地模型单次 50–200ms，看起来不慢。但 Agent 一次轮次里工具调用是成串的——5 个工具 × 200ms = 主循环阻塞 1 秒。

用户看到的是：流式输出突然停了。🧵

**2/4**
拆成子进程之后，三个决策花了我最多时间：

① child process 还是 worker thread？
→ child process。embedding 几百兆常驻内存，GC 一次卡一秒。而且子进程能独立崩溃。

② 怎么知道 Worker 起来了？
→ stdout 关键字 + HTTP /health 轮询，双信号。

③ 怎么优雅退出？
→ SIGTERM + 3 秒后 SIGKILL。SIGTERM 是请求，SIGKILL 才是命令。

**3/4**
最大的认知转变：进程模型不是后端内部细节，是前置 UX 决策。

第一版：两个终端 + 手动配置 hook
第二版：`--with-memory` 一条命令

工程量差不多，用户体感差一个量级。你的进程模型直接决定了用户的命令行长度。

**4/4**
判断标准：副路径里有没有 > 100ms 的阻塞操作？

有 → 拆进程
没有 → 别拆，IPC 开销不值得

WorkerManager 一共 130 行，可以直接抄。全文 + 代码 👇

## 第三篇（权限系统）

### X / 即刻 thread（4 条）

**1/4**
AI Agent 的权限系统，第一版我写错了。

做法：框架维护一份 dangerous_tools 列表，命中就弹确认。

结果：`bash echo hello` 也问。`bash git status` 也问。用户按 y 按到想砸键盘。🧵

**2/4**
根本问题：`bash rm -rf /` 和 `bash cat file` 是同一个工具，但风险完全不同。

框架去判断"bash 危不危险"，无论怎么判断都不对。

正确做法：让工具自己分类。bash 看命令前缀，write 看路径 glob。框架只问一句话，工具自己回答。

**3/4**
第二个错误：权限做成布尔值。

实际需要三态：
- allow：直接放行
- deny：拒绝（AI 会换方式做）
- ask：需要用户确认

ask ≠ deny。折叠进 deny，AI 以为永远不通过，开始绕路。折叠进 allow，危险操作偷偷执行。

**4/4**
最终的权限引擎：22 行。

每个工具自己实现 checkPermissions + preparePermissionMatcher。用户每按一次 y，自动生成一条 AllowRule，下次相同模式直接放行。

权限规则不是用户配置出来的，是用户用出来的。

## 第四篇（工具调度）

### X / 即刻 thread（4 条）

**1/4**
AI Agent 的工具调度，我试了三种方案。前两种都错了。

❌ 全串行：正确但慢。读三个文件 50ms 能搞定，串行变 150ms。
❌ 框架维护安全列表：`bash` 是安全还是不安全？取决于命令内容。框架猜不了。

✅ 让工具自己声明。🧵

**2/4**
关键设计：`isConcurrencySafe(input)` 接收输入。

同一个 bash 工具：
- `git status` → return true
- `rm -rf foo` → return false

判断粒度不是工具，是工具调用。如果签名无参数，bash 只能选保守的 false，损失全部并发收益。

**3/4**
默认值必须保守：

```
isConcurrencySafe: spec.isConcurrencySafe ?? (() => false)
```

忘记声明的代价是慢，不是炸。反过来默认 true，每加一个新工具都可能引入并发 bug。

MCP 工具也默认 false——语义对我们完全不透明，假设它危险是唯一安全的选择。

**4/4**
最后一个反直觉的决定：不做部分并行。

全部安全 → Promise.all
否则 → 全部串行

5 行代码解决 80% 的问题。实际跑下来，95% 的 batch 要么全是 read（全并行），要么含 write（全串行）。混合 batch 罕见，不值得写拓扑排序。

## 第五篇（记忆系统）

### X / 即刻 thread（5 条）

**1/5**
给 AI Agent 做记忆系统，我做了三个版本。

v1 关键词匹配：上次说"重构认证模块"，这次问"auth 改了什么"——找不到。"认证"和"auth"字面不命中。

存活三天就删了。🧵

**2/5**
v2 换向量搜索，语义匹配好了。但新问题：召回太多噪音。

我问"auth 改了什么"，它把三天前的 git status、一周前的 ls、两周前的无关 grep 全拉出来。注入到 prompt 里，模型反而被干扰了。

召回率高 ≠ 有用。

**3/5**
阈值调参：

0.7 → 什么都召不回
0.5 → 漏掉太多
0.3 → 刚好
0.1 → 噪音爆炸

0.3 不是算出来的，是用真实对话跑了二十多次试出来的。换模型、换 chunking、换对话风格，这个数字都会变。

**4/5**
最关键的一步：不存原始工具日志，用 LLM 提炼成结构化观察再存。

原始：`grep -r 'validateToken' src/ → src/auth/middleware.ts:...`
提炼后：`用户在搜索 validateToken 的引用位置，可能在准备重构认证逻辑`

后者的 embedding 质量高一个量级——因为它包含意图，不只是事实。

**5/5**
记忆系统的真正难点不是"怎么存"也不是"怎么查"。

是怎么控制注入到 system prompt 里的信噪比。

每一条记忆都在消耗 token 预算，都在跟当前任务竞争注意力。存储随便选，阈值必须调，格式必须设计。

## 第六篇（Hook 系统）

### X / 即刻 thread（4 条）

**1/4**
AI Agent 需要插件系统。第一反应是 EventEmitter。

我没用。我用了 shell 命令：

```
'post-tool-use': [{
  command: 'curl -X POST http://localhost:37777/...',
  onError: 'ignore',
  timeout: 3000
}]
```

看起来很丑。但这是我做过的最正确的架构决策之一。🧵

**2/4**
EventEmitter 三个致命问题：

① 插件必须跟 Agent 同进程（记忆系统跑在独立 Worker 里）
② 插件必须用同一种语言（想用 Python 写分析？做不到）
③ 插件崩溃拖垮主进程（shell 命令天然隔离）

shell 命令全部解决。代价是"看起来丑"。

**3/4**
数据怎么传？

小数据 → 环境变量（$TOOL_NAME, $SESSION_ID）
大数据 → stdin/stdout

环境变量零解析成本，自文档化，有大小限制（这是优点——强制你只传必要数据）。

不要统一成一种格式。两种场景约束不同。

**4/4**
这套系统上线两个月，核心代码零修改。期间加了 7 个 hook。

每次都是加一条配置，不动框架。

最好的插件系统是最笨的那个。不要发明协议，不要定义接口，不要写 SDK。给一个 shell，传几个环境变量，收一个 stdout。够了。
